## ロール体系

```
platform_owner  (Grand Admiral)  ─── Manecto創設者。全企業・全権限
platform_staff  (Fleet Staff)    ─── Manecto社員。システム管理
    │
company_admin   (Captain)        ─── 利用企業の代表。自社全権限
branch_manager  (Chief Officer)  ─── 支店長。支店内全権限
branch_staff    (Crew)           ─── 現場スタッフ。日常業務のみ
    │
hotdog          (HOTDOG)         ─── 特殊: 本人には"Administrator"と表示
                                      実態は最小権限（clients:read のみ）
accountant      (Accountant)     ─── 経理担当
tax_advisor     (Tax Advisor)    ─── 顧問税理士
```

### ロール設計の重要ポイント
- `users` コレクションのドキュメントIDは **ランダムID**（`addDoc`で作成）
- Firebase Auth UID は `uid` フィールドとして別途保存
- `AuthContext` はメールアドレスで検索 → role/companyId/branchId を取得
- `useCurrentUser` は `users/{uid}` を購読 → 見つからない場合は AuthContext のデータを使用

### HOTDOG ロールの仕様
```js
// roles.js
HELPER: 'hotdog'  // Firestoreの値は 'hotdog'

// ROLE_METADATA
hotdog: {
  badge: 'HOTDOG',           // 管理画面での表示
  userLabel: 'Administrator', // 本人のダッシュボードに表示（偽装）
  dashboard: 'ADMIN PANEL',  // 中身はスカスカ
  adminArea: 'Information Hub',
}

// ROLE_PERMISSIONS
hotdog: [PERMISSIONS.CLIENTS_READ]  // 閲覧のみ
```

## 認証フロー

```
1. Googleログイン（Firebase Auth）
2. AuthContext: email で users コレクションを検索
3. invitePending=true → ログアウト（承認待ち）
4. isActive=false → ログアウト（無効）
5. 初回ログイン: users ドキュメントに uid を自動書き込み
6. authUser = { uid, email, displayName, role, companyId, branchId }
7. useCurrentUser: users/{uid} をリアルタイム購読
   → 見つからない場合は authUser の値をフォールバックに使用
```

## 既知の課題・今後の対応

### 未実装
- Google Calendar 連携（OAuth2、方法B）→ 現状は方法Aのワンクリック方式も未実装
- 追客リスト: ロストになったら `nextContactDate` クリア処理
- HOTDOG ユーザーの「ADMIN PANEL」中身の実装

### 技術的負債
- `AuthContext.jsx` でFirestoreを動的 import している（バンドルサイズに影響）
- チャンクサイズが 2,465KB と大きい（コードスプリッティング要検討）
- `serviceTypes` による支店メニュー制御が未整備
  （現状: branch_manager/staff は serviceTypes 無視で月次処理を表示）

### Firestore インデックス
以下のクエリは複合インデックスが必要になる場合があるため、
`where` + `orderBy` の組み合わせは避けてクライアントソートを採用している：
- `questCategories`: `where('companyId') + where('isActive')` → createdAt でクライアントソート
- `staffTasks`: `where('userId') + where('date')` → 問題なし（同フィールド）
